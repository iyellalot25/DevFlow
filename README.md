# DevFlow

**Turn a vague engineering task into a tracked, structured checklist — in seconds, not minutes.**

DevFlow is a multi-user backend system for teams that plan software work in one-liners and forget to break them down until it's too late. Describe a task in plain English, let a narrowly-scoped AI job decompose it into concrete implementation steps, then track, update, and report on progress — all through a real REST API backing a live dashboard.

> 🔗 **Live demo:** [https://devflow-l22x.onrender.com](https://devflow-l22x.onrender.com) — free-tier hosting, so the first request after idle may take ~30–50s to wake up.

---

## The problem

Developers describe work like _"move the API to Postgres and dockerize it"_ — one sentence — and then have to manually translate that into an actual checklist before starting. That translation step gets skipped under time pressure, which is exactly when a task most needs to be broken down properly.

DevFlow automates that one step: a task description goes in, a structured implementation checklist comes out, backed by a real system for tracking it to completion.

**The 10x claim:** turning an unstructured task into an actionable checklist drops from several minutes of manual planning to seconds. That's specifically about the planning step — DevFlow doesn't write or modify code, and it never will (see [Guardrails](#guardrails-on-the-ai)).

---

## What it does

- **AI task decomposition** — paste a vague task, get back a structured, ordered list of implementation subtasks, generated by an LLM whose only job is decomposition.
- **Team collaboration** — join a team with a shareable code, share projects and progress with teammates in real time.
- **Live updates** — every teammate's dashboard updates instantly via Server-Sent Events when anything changes — no polling, no refresh button.
- **Full project/task/subtask CRUD** — create, edit, and delete at every level, all scoped to your team.
- **Bring-your-own API key** — teams can plug in their own Gemini key (encrypted at rest with AES-256-GCM) instead of sharing a default quota.
- **Usage dashboard** — daily quota, lifetime token counts, all visible in the UI.
- **PDF progress reports** — a designed, typographic report generated on demand from live data: stat summary, two-segment progress bars, color-coded subtask markers.
- **Cookie-based auth with silent refresh** — no re-login every hour; sessions renew transparently.
- **Containerized & deployed** — one `docker compose up` spins up the entire stack locally; the same Dockerfile runs it in production.

## Architecture

```
Browser (public/index.html — vanilla JS, no framework, no build step)
        │
        │  fetch() with httpOnly cookies  +  EventSource (SSE)
        ▼
Express app (app.js)
        │
        ├─ routes/*.js        thin HTTP layer, cookie-auth protected
        │
        ├─ services/*.js      business logic, SQL, team-ownership checks,
        │                     encryption, usage/quota logic
        │
        ├─ sseService.js      in-memory per-team connection registry
        │                     + broadcast() called from every mutating route
        │
        ├─ db.js              pg connection pool
        │                     ▼
        │                PostgreSQL (Neon in production, Dockerized locally)
        │
        └─ worker.js          DB-polling background loop for AI decomposition
                              jobs — FOR UPDATE SKIP LOCKED claim pattern,
                              orphaned-job recovery on startup
```

**Deployed on:** Render (containerized app, free tier) + Neon (managed Postgres, free tier). Zero paid infrastructure anywhere in the stack.

## Engineering highlights

Six core backend concepts, each implemented for real rather than stubbed:

| Concept             | Where it lives                                                                                       | What's real about it                                                                                                                         |
| ------------------- | ---------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **REST API**        | `routes/*.js`                                                                                        | Correct status codes (`201`/`204`/`400`/`401`/`404`/`429`), consistent error shape, input validation on every write                          |
| **Database**        | `schema.sql`, `services/*.js`, `db.js`                                                               | Real foreign-key constraints, parameterized queries throughout, data survives a restart                                                      |
| **Authentication**  | `middleware/auth.js`, `services/authService.js`, `routes/auth.js`                                    | JWT access + opaque refresh tokens, both httpOnly cookies; refresh tokens hashed at rest; every protected route verified, not just decorated |
| **Background jobs** | `worker.js`, `services/decompositionProcessor.js`                                                    | Real DB-polling claim pattern (`FOR UPDATE SKIP LOCKED`), safe under multiple workers, orphaned-job recovery on startup                      |
| **PDF reporting**   | `services/pdfService.js`, `routes/reports.js`                                                        | Generated from live persisted data on request — not cached, not a static template                                                            |
| **LLM integration** | `services/llmService.js`, `services/decompositionValidator.js`, `services/decompositionProcessor.js` | Narrow single-purpose prompt, two-layer output validation before anything is trusted or persisted, per-team token/cost logging               |

**Also implemented, beyond the core six:**

- Team collaboration via shareable join-codes, with creator-only administrative actions
- Real-time updates via Server-Sent Events
- Per-team API quota enforcement with clean `429` responses
- Encrypted bring-your-own API key storage (AES-256-GCM)
- Rate limiting on auth endpoints
- Full containerization with a healthcheck-gated Docker Compose stack
- Live deployment on free-tier infrastructure

## Guardrails on the AI

The LLM has exactly one job: turn a task description into a list of subtask strings. It never sees the codebase, never writes code, and never runs anything. Every response is:

1. Requested in a specific, constrained output shape
2. Independently re-validated against that shape before being trusted (`decompositionValidator.js`) — a malformed or unexpected response fails the job cleanly instead of corrupting data
3. Logged for token usage and cost, per team, per job

If a team plugs in their own API key, it's encrypted at rest (AES-256-GCM) and decrypted only server-side — it's never returned to any client, ever.

## Getting started

### Prerequisites

- Node.js v18+
- Docker + Docker Compose
- A free Google Gemini API key ([aistudio.google.com](https://aistudio.google.com/apikey))

No paid services required anywhere.

### Setup

```bash
git clone https://github.com/iyellalot25/DevFlow
cd devflow
npm install
cp .env.example .env   # then fill in real values
```

### Environment variables

| Variable                                              | Description                                                                                                                     |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `DATABASE_URL`                                        | Postgres connection string used when running the app directly on the host (`npm run dev`)                                       |
| `DATABASE_URL_DOCKER`                                 | Postgres connection string used when the app itself runs inside Docker (points at the `postgres` service name, not `localhost`) |
| `JWT_SECRET`                                          | Long random string used to sign access tokens                                                                                   |
| `GEMINI_API_KEY`                                      | Your Gemini API key — the shared/default key used when a team hasn't set its own                                                |
| `ENCRYPTION_KEY`                                      | 64-character hex string (32 bytes) — AES-256-GCM key used to encrypt team-provided Gemini keys at rest                          |
| `PORT`                                                | Port the Express server listens on (default `3000`)                                                                             |
| `NODE_ENV`                                            | Set to `production` in production only — affects cookie `secure` flag                                                           |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | Used by Docker Compose to initialize the local Postgres container                                                               |

Generate a safe `ENCRYPTION_KEY` with:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

### Run it — two ways

**Option A — full stack in Docker (closest to production):**

```bash
docker compose up -d --build
```

Spins up the app and Postgres together, applies the healthcheck, and serves at `http://localhost:3000/`.

**Option B — Postgres in Docker, app on the host (faster iteration):**

```bash
docker compose up -d           # Postgres only
docker exec -i devflow-postgres psql -U devflow -d devflow < schema.sql
npm run dev
```

Either way, the app is available at `http://localhost:3000/`.

## 5-minute demo path

1. Register a new account at `http://localhost:3000/` — optionally paste a teammate's join code, or leave it blank to start a new team.
2. Create a project, e.g. _"Backend Migration"_.
3. Add a task with a real, vague description: _"Move my Express API from SQLite to PostgreSQL, keep the existing endpoints working, and dockerize it."_
4. Click **Decompose with AI** — watch the job status update live and the generated subtasks appear within a few seconds.
5. Mark a couple of subtasks `in_progress` / `done` — watch the two-segment progress bar update instantly, including on a second browser tab open to the same team (real-time, via SSE — no refresh needed).
6. Copy your team's join code, open the app in a private/incognito window, register a second account with that code, and watch both dashboards update as you make changes in either.
7. Download the PDF report and confirm it reflects current progress.

## API reference

Every route except `/auth/register`, `/auth/login`, and `/health` requires a valid session, sent automatically via httpOnly cookies (no manual header needed once logged in). A `401` triggers an automatic silent refresh via `/auth/refresh` on the frontend; if that also fails, the user is logged out. Every resource lookup is scoped to the caller's own team and returns a plain `404` — not `403` — for another team's resource, so a caller can't distinguish "doesn't exist" from "exists but isn't yours."

All error responses share one shape: `{ "error": "message" }`.

### Auth

| Method | Path             | Notes                                                                                                                 |
| ------ | ---------------- | --------------------------------------------------------------------------------------------------------------------- |
| `POST` | `/auth/register` | Body: `{ email, password, join_code? }`. Rate-limited (10/15min/IP). `join_code` optional — omit to start a new team. |
| `POST` | `/auth/login`    | Body: `{ email, password }`. Rate-limited (10/15min/IP).                                                              |
| `POST` | `/auth/refresh`  | Rotates the access token using the refresh-token cookie.                                                              |
| `POST` | `/auth/logout`   | Revokes the refresh token server-side and clears cookies.                                                             |
| `GET`  | `/auth/me`       | Returns the current session's user info.                                                                              |

### Projects

| Method   | Path            | Notes                          |
| -------- | --------------- | ------------------------------ |
| `POST`   | `/projects`     | Body: `{ name, description? }` |
| `GET`    | `/projects`     | Team's projects                |
| `PATCH`  | `/projects/:id` | Partial update                 |
| `DELETE` | `/projects/:id` | Cascades to tasks/subtasks     |

### Tasks

| Method   | Path                         | Notes                       |
| -------- | ---------------------------- | --------------------------- |
| `POST`   | `/projects/:projectId/tasks` | Body: `{ raw_description }` |

| `PATCH`  | `/tasks/:id`                 | Partial update              |
| `DELETE` | `/tasks/:id`                 | Cascades to subtasks        |

| -------- | ------------------------- | ----------------------------------------------------- |

| `PATCH`  | `/subtasks/:id`           | Body: `{ status: "todo" \| "in_progress" \| "done" }` |
| `DELETE` | `/subtasks/:id`           |                                                       |

### AI decomposition & usage

| Method | Path                       | Notes                                                                                              |
| ------ | -------------------------- | -------------------------------------------------------------------------------------------------- |
| `POST` | `/tasks/:taskId/decompose` | `202`, queues a background job. `429` if the team's daily quota is exhausted.                      |
| `GET`  | `/jobs/:id`                | Poll for job status: `pending` / `processing` / `done` / `failed`. `result` populated when `done`. |
| `GET`  | `/usage`                   | Today's quota usage, lifetime job count, lifetime token totals                                     |

### Teams

| Method   | Path                     | Notes                                                                                                                                    |
| -------- | ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `GET`    | `/teams/me`              | Current team, members, join code                                                                                                         |

## Design decisions

- **DB-polling worker instead of a message queue** (Redis, SQS, etc.) — keeps the stack free and simple while still implementing a real async job pattern; jobs are claimed with `FOR UPDATE SKIP LOCKED` so it stays correct even with multiple worker processes.
- **Cookies over JSON-body tokens** — httpOnly cookies for both access and refresh tokens are immune to XSS token theft in a way `localStorage` never is; the tradeoff is CSRF surface, mitigated here with `sameSite: lax`.
- **Opaque, hashed refresh tokens** in their own table, not just a longer-lived JWT — a leaked refresh token is useless without the corresponding DB row, and it's revocable server-side (logout actually invalidates something).
- **Server-Sent Events over WebSockets** — DevFlow only ever needs server→client push ("something changed, go refetch"), never client→server messaging over the same channel. SSE gets this for free over plain HTTP, with automatic reconnection built into the browser's `EventSource`.
- **"Refetch on event" instead of patched state** — the frontend doesn't try to surgically apply each SSE payload to local state; it just refetches the affected resource. Simpler, harder to get subtly wrong, and cheap enough at this scale.
- **Team model via shareable join-codes, not email invitations** — no email service required, works entirely within the `$0` constraint, and is a smaller surface to get right.
- **Quota is about DevFlow's own usage tracking, not billing** — the daily decomposition quota applies per team even when a team supplies its own Gemini key; it's a usage-shape decision, not a cost-passthrough mechanism.
- **AES-256-GCM for stored API keys, decrypted only server-side** — a team's own Gemini key is never returned to any client in any response, only used internally when calling the LLM.
- **Two-layer LLM output validation** — the model is asked for a specific shape, and the response is independently re-validated (`decompositionValidator.js`) before anything touches the database. The LLM's output is never trusted blindly.
- **Replace-on-redecompose for subtasks** — re-running AI decomposition on an already-decomposed task deletes the previous AI-generated subtasks before inserting the new batch, inside the same transaction (so a failed insert rolls back to the previous state instead of leaving zero subtasks). This is a deliberate "decompose = regenerate the plan" semantic, not append-or-merge.
- **PDFKit over a headless-browser renderer** (e.g. Puppeteer) — no Chromium dependency, far lighter for a small structured report.
- **Vanilla JS frontend, no framework, no build step** — a React migration was considered and explicitly rejected to keep the Docker setup single-stage and the whole project buildable and runnable with nothing beyond Node and Docker.

## Known limitations

- Removing a team member doesn't immediately invalidate their existing session — their access-token cookie remains valid for up to its 1-hour lifetime. Accepted tradeoff for not maintaining a server-side revocation list on every request.
- No ownership-transfer mechanic — if a team's creator leaves while others remain, no one inherits creator-only privileges (removing members, regenerating the join code) on that team going forward.
- Server-Sent Events use an in-memory connection registry, so real-time updates work correctly on a single server instance (true of the current Render deployment) but would need a shared pub/sub layer (e.g. Redis) to scale beyond one instance.
- Render's free tier sleeps after 15 minutes of inactivity — the first request after idle takes 30–50 seconds to wake up.
- No automated test suite yet — all endpoints and error paths have been verified manually and are documented above; a Jest + Supertest suite with CI is the top item in Future Ideas.

## Security

- Passwords hashed with bcrypt; plaintext passwords are never stored or logged.
- Access and refresh tokens delivered as httpOnly cookies — never exposed to client-side JavaScript.
- Refresh tokens stored hashed, individually revocable, with server-side logout.
- Team-provided Gemini API keys encrypted at rest with AES-256-GCM, decrypted only server-side, never returned in any API response.
- All SQL uses parameterized queries — no string-concatenated SQL anywhere.
- Every protected route validates the session and independently re-checks that the requested resource belongs to the caller's team.
- Rate limiting on `/auth/login` and `/auth/register` (10 attempts / 15 minutes / IP).
- Secrets read only from environment variables — `.env` is git-ignored, `.env.example` ships with placeholders only, and nothing is ever printed to logs.
